# The Customer Account schema comes from the consumer's own app

> ⚠️ **SUPERSEDED by [ADR-0014](./0014-the-customer-account-schema-is-a-committed-standard-tier-fixture.md).** This ADR's central decision — that the schema comes from the consumer's own `customerAccountApiClientId` — is **not implementable**. The introspection service takes an _app API key_ from Partners → Authentication, a disjoint namespace, and returns `404` for the shop-configured customer-account client id this ADR names. Refuted in [#42](https://github.com/KookiKodes/solidifront/issues/42), re-decided in [#43](https://github.com/KookiKodes/solidifront/issues/43).
>
> Also void: the **"Why the consumer's client id, not Hydrogen's"** section, and **"Why the pipeline is optional"** — the pipeline is now unconditional, because its stated reason ("a storefront without login must not need a Customer Account app registered in order to build") no longer applies when no consumer registers anything.
>
> And void: this ADR's claim that `storefrontCustomerAccessTokenCreate` is **"load-bearing for buyer identity"**. It is not load-bearing for anything — the Customer Account access token reaches `@inContext` directly, and solidifront never calls the mutation. [ADR-0015](./0015-the-customer-account-access-token-is-the-buyer-identity-credential.md), from [#45](https://github.com/KookiKodes/solidifront/issues/45).
>
> **Still standing**, and carried forward by ADR-0014: the welded version, retired-pin-is-a-build-error, the arrival oracle, fall-forward-is-silent-on-the-schema-path, no-fallback, no-`mock.shop`-equivalent, and the `@inContext` argument-set reading. Retained below for the reasoning behind those.

Customer Account API types are generated by introspecting Shopify's schema service with **the consumer's own Customer Account app client id** — the same one they already configure for OAuth — at the version pinned by [ADR-0005](./0005-the-api-version-type-is-open-and-narrowed-by-codegen.md). Solidifront vendors no CAAPI schema and ships none to consumers. Decided in [#34](https://github.com/KookiKodes/solidifront/issues/34).

```
GET https://app.myshopify.com/services/graphql/introspection/customer
      ?api_client_api_key={the consumer's customerAccountApiClientId}
      &api_version={the pinned version}
```

Tokenless: no OAuth, no store credential, no access token. Verified `200` with a standard introspection payload.

## Why this endpoint exists in the design at all

Because the alternative solidifront shipped was already broken. `packages/codegen/copy-files.json` vendored `customer-account.schema.json` from Hydrogen's `main` branch by URL, with no automation — pinned at 2025-10-04 and **392 types**, against **478** at `2026-10`. That is +103/−17, and the removed types include `Checkout`, `AppliedGiftCard` and `CustomerMailingAddress`: the committed schema described types Shopify no longer serves. The URL was also on a disappearing path, since `hydrogen-react` exists only on `main` and the `preview` rewrite drops the package.

[ADR-0006](./0006-an-operation-is-a-generated-module-not-a-string.md) had already ruled the vendored schemas deleted rather than relocated. This ADR supplies the mechanism that makes deletion possible.

## Why the consumer's client id, not Hydrogen's

The service requires a _real_ Customer Account app client id — a fabricated one returns `404`, an omitted one `400`. Hydrogen hardcodes its own public id for this purpose (`references/hydrogen/packages/hydrogen/codegen.ts:8`), and copying that value would work today.

It is rejected on three grounds. It reintroduces a Hydrogen dependency, which the "own the core" constraint exists to forbid. The id is a third party's to revoke or rate-limit. And most substantively, an id we do not control may not describe the app that will actually issue the queries — if the returned schema varies with the app's granted scopes, a borrowed id generates types for capabilities the consumer's app does not have. The consumer's own id makes that class of mismatch unrepresentable, and costs them nothing: [ADR-0012](./0012-customer-authentication-is-a-requirement-not-an-argument.md) already requires the id for OAuth.

## Why the pipeline is optional

No customer-auth configuration means no CAAPI codegen, and a CAAPI operation then fails to compile. A storefront without login must not need a Customer Account app registered in order to build.

The gate is not new machinery — ADR-0012 makes an authenticated customer a **requirement in the `R` channel**, so a consumer who never configures CAAPI can never satisfy it. This aligns codegen with a boundary the type system already draws. The rejected alternative is worse than it looks: falling back to solidifront's committed fixture when no client id is present would serve _our_ schema as _their_ types, which is precisely the vendored-schema staleness this ADR exists to end.

## Consequences

**Fall-forward is silent here, unlike the data path.** The response carries no `x-shopify-api-version` echo, and the service implements Shopify's documented fall-forward to the oldest accessible stable version — every version from `2024-01` through `2025-10` currently returns one byte-identical schema. So a retired pin yields a schema for a different version with no local signal whatsoever. Nothing can detect this on the CAAPI side; ADR-0005's registry check is the only guard, which is why a retired pin is an error there rather than a warning.

**The endpoint is undocumented and has no fallback.** It appears nowhere in Shopify's versioning, Customer Account, or headless documentation — it is known only from Hydrogen's source. Unlike the Storefront path, which has introspection _and_ a direct proxy, there is no second source. It is therefore a declared external dependency under the treatment set by [#29](https://github.com/KookiKodes/solidifront/issues/29): pinned, diffed in the nightly, failing with a directed error if it moves. **This is the single point of failure for the customer-auth pillar.**

> ⚠️ **Both halves of this paragraph are now false.** [#44](https://github.com/KookiKodes/solidifront/issues/44) found **three** routes to a standard-tier schema, two of them keyless — the `@shopify/dev-mcp` tarball, the borrowed app key, and shopify.dev's per-version docs corpus — so there is a fallback chain and the pillar is not a single point of failure. "Undocumented" is also softened: the app-key service is README-documented in a published first-party package. See [ADR-0014](./0014-the-customer-account-schema-is-a-committed-standard-tier-fixture.md).

**Version enumeration is an arrival oracle only.** Valid versions return `200`, unreleased ones `404` — so a new CAAPI version becoming available is detectable by probe, and the canary in ADR-0005 extends to cover it. Retirement is _not_ detectable this way, because retired versions keep returning `200` via fall-forward; registry absence is the retirement signal.

**CI cannot use the consumer path, and there is no `mock.shop` equivalent.** Solidifront's own CI has no store and no app. It therefore commits one introspection JSON per supported version as a fixture — the same rule [ADR-0006](./0006-an-operation-is-a-generated-module-not-a-string.md) sets for Storefront — generated from an app id the maintainers control. Solidifront's own CAAPI operations validate against every supported version, with no exception carved for CAAPI; `storefrontCustomerAccessTokenCreate`, which ADR-0012 makes load-bearing for buyer identity, was verified present across the entire window.

**`@inContext` confirms the read-from-the-schema rule rather than testing it.** CAAPI's directive takes `country, language, preferredLocationId` at `2026-04` through `2026-10`, and **five** arguments at `unstable` (adding `channelId, buyer`). The argument set is a property of the pinned version, exactly as [ADR-0007](./0007-incontext-is-injected-at-build-time-from-the-pinned-schema.md) requires; any fixed list — including "CAAPI has three" — would already be wrong.

**Unverified:** whether the service accepts an _arbitrary_ consumer's client id, or only ids Shopify has enrolled. Every probe here used Hydrogen's public id, the only one available. If arbitrary ids are refused, the fallback is a solidifront-registered app id, and this ADR's "why the consumer's client id" section is what would have to change.
